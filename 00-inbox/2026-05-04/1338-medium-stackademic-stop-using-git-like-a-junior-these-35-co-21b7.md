# Stop Using Git Like a Junior. These 35 Commands Will Change How Your Team Ships

<figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*vxualyrVgMQm7RH-ntppog.png" /></figure><h4>Most engineers use 5 Git commands daily and wonder why deploys are messy. Here’s the full toolkit senior engineers actually use in production</h4><p>Here’s a uncomfortable truth about how most engineers use Git.</p><p>They learned it under pressure — a bootcamp, a first job, a tutorial that covered the basics. They internalized git add, git commit, git push, git pull, git merge. Maybe git stash if they felt adventurous.</p><p>And then they stopped.</p><p>They’ve been using the same five commands for three, five, sometimes ten years. Not because Git doesn’t have more to offer — it has significantly more to offer — but because nobody ever showed them what they were missing, and the five commands were enough to get the job done.</p><p>Until they weren’t.</p><p>Until the merge conflict took two hours to resolve and shouldn’t have. Until the wrong commit went to production and nobody could figure out which one. Until a hotfix had to go out at midnight and the branching strategy fell apart under pressure. Until a junior engineer accidentally pushed directly to main and the team lost forty minutes recovering.</p><p>I’ve watched all of these happen. In good teams. With experienced engineers. Using Git every single day.</p><p>The problem isn’t Git. The problem is that most engineers are using a Formula 1 car to drive to the grocery store, and they’ve never left second gear.</p><h3>Why This Matters More Than You Think</h3><p>Git isn’t just version control. In a production engineering context, Git is your audit trail, your rollback mechanism, your collaboration protocol, and your deployment trigger — all at once.</p><p>When something goes wrong in production at 3 AM, your Git history is often the first place you look. When a bug ships that shouldn’t have, the answer is almost always in a commit. When you need to deploy a hotfix without shipping unfinished features, your branching strategy either saves you or betrays you.</p><p>The engineers who handle incidents cleanly, who ship with confidence, who can surgically revert a specific change without touching anything else — they’re not using different software. They’re using Git differently.</p><p>Here’s what that actually looks like.</p><h3>The Commands You Use vs. The Commands You Should</h3><h3>Investigation: Finding What Actually Changed</h3><p>The first thing senior engineers do when something breaks in production is trace it to a specific change. This is where most engineers waste time, because they’re reading commit logs with their eyes instead of asking Git to do the work.</p><p><strong>git log --oneline --graph --decorate --all</strong></p><p>This gives you a visual branch graph in the terminal. Not beautiful, but functional. You can see at a glance how branches have diverged, which commits are on which branch, and where your HEAD is sitting. When you’re trying to understand the state of a messy repository, this is the first command to run.</p><p><strong>git log -S &quot;function_name&quot; --all</strong></p><p>Pickaxe search. This finds every commit that added or removed a specific string — a function name, a variable, a configuration value. When a bug appears and you know which function is affected but not when it changed, this finds it in seconds. I’ve used this to trace bugs to commits from 18 months ago that nobody remembered making.</p><p><strong>git log --since=&quot;2 days ago&quot; --author=&quot;devrim&quot; --oneline</strong></p><p>Filter commits by author and time window. Useful during incidents when you need to quickly see what a specific person shipped recently. Also useful for code reviews when you want to catch up on what someone did while you were out.</p><p><strong>git diff main...feature-branch</strong></p><p>Three dots, not two. Two dots shows the diff between two points. Three dots shows what’s on the feature branch that isn’t on main — which is almost always what you actually want when reviewing a PR or understanding what a branch will add.</p><p><strong>git blame -L 40,60 src/PaymentService.java</strong></p><p>Blame with a line range. Everyone knows git blame. Few people use the -L flag to restrict it to specific lines. When a production bug is in a 600-line file and you know it's somewhere around line 45, this is the command.</p><h3>Recovery: Undoing Without Destroying</h3><p>This is where the stakes are highest and where most engineers freeze. Something went wrong. You need to fix it. You’re not sure which command to use and you’re afraid of making it worse.</p><p><strong>git revert &lt;commit-hash&gt;</strong></p><p>The safe undo. Creates a new commit that reverses the changes from a specific commit. The original commit stays in history — you’re not rewriting anything. This is what you use when you need to undo something that already shipped to production and you can’t afford any ambiguity in the history. revert is safe. Use it by default.</p><p><strong>git reset --soft HEAD~1</strong></p><p>Moves HEAD back one commit but keeps your changes staged. The commit disappears, the changes don’t. Use this when you committed too early and want to amend what you’re including. Never use this on commits that have already been pushed to a shared branch.</p><p><strong>git reset --hard HEAD~1</strong></p><p>Moves HEAD back one commit and discards the changes entirely. The nuclear option for local work. If you pushed this to a shared branch, you’ll need a force push, which will cause problems for everyone who has pulled the branch. Think twice.</p><p><strong>git cherry-pick &lt;commit-hash&gt;</strong></p><p>Takes a specific commit from anywhere in the repository and applies it to your current branch. The hotfix workflow: fix the bug on a hotfix branch, cherry-pick it to main, cherry-pick it to the release branch if needed. Clean. Surgical. No risk of pulling in unrelated changes.</p><p><strong>git reflog</strong></p><p>The safety net that most engineers don’t know they have. reflog shows every place HEAD has been, even after resets and rebases. If you've done a hard reset and regret it, reflog lets you find the commit hash and recover it. I've used this to recover work that felt permanently lost. It's one of the most important commands in Git and one of the least known.</p><h3>Branching: Shipping With Confidence</h3><p>The difference between a team that deploys on Fridays without fear and a team that freezes before every deploy is usually the branching strategy — and how well everyone actually follows it.</p><p><strong>git branch --merged main</strong></p><p>Lists branches that have been fully merged into main. Run this monthly. Stale branches accumulate silently. A repository with 200 branches is a repository where nobody can see what’s actually in flight, and where “I thought that was already merged” becomes a regular source of confusion.</p><p><strong>git branch -d $(git branch --merged main | grep -v main)</strong></p><p>Deletes all locally merged branches in one command. Run this after every sprint or release cycle. A clean repository is a repository where the current state of work is visible at a glance.</p><p><strong>git push origin --delete old-feature-branch</strong></p><p>Deletes the remote branch. git branch -d only deletes locally. If the branch exists on the remote (it usually does), this is how you clean it up there too.</p><p><strong>git switch -c feature/payment-refactor</strong></p><p>The modern replacement for git checkout -b. Does the same thing — creates and switches to a new branch — but with clearer intent. switch is for branches; restore is for files. The separation makes the intent of each command explicit.</p><p><strong>git stash push -m &quot;WIP: payment timeout handling&quot;</strong></p><p>Named stashes. If you’re stashing more than one thing, unnamed stashes become a stack you can’t navigate. Name them. git stash list becomes readable. git stash pop stash@{1} becomes something you can do without guessing.</p><h3>Collaboration: Making Reviews Faster</h3><p>Code review is where most of the friction in a team’s shipping process lives. These commands don’t write better code — they make the review process less painful.</p><p><strong>git fetch --all --prune</strong></p><p>Fetches all remote branches and removes local references to remote branches that no longer exist. Run this before starting any work. Your local view of the repository should reflect reality, and --prune ensures deleted remote branches don't keep showing up in your branch list.</p><p><strong>git rebase -i HEAD~5</strong></p><p>Interactive rebase. The command that turns five messy “WIP”, “fix”, “actually fix”, “please work”, “ok this time” commits into one clean commit with a meaningful message before the PR goes up for review. This is not about deceiving history — it’s about respecting your reviewer’s time and making the eventual git blame useful for future engineers.</p><p>Use this on local commits that haven’t been pushed. Once commits are on a shared branch, rebasing them rewrites history and causes problems for everyone who has pulled the branch.</p><p><strong>git commit --fixup &lt;commit-hash&gt;</strong></p><p>Creates a commit that’s explicitly marked as a fixup for a specific earlier commit. When combined with git rebase --autosquash, these fixup commits automatically get squashed into the commits they're fixing. Useful workflow: make a commit, push for review, get feedback, make fixup commits, squash before merging.</p><p><strong>git log --follow src/PaymentService.java</strong></p><p>Log for a specific file, following renames. If a file was renamed at any point in its history, git log without --follow won't show commits before the rename. --follow traces the file through renames, giving you the complete history of what happened to that file regardless of what it was called.</p><h3>Production: The Commands That Matter at 3 AM</h3><p>These are the commands you run when something is actively broken and every minute costs money.</p><p><strong>git bisect start</strong> <strong>git bisect bad</strong> <strong>git bisect good &lt;last-known-good-commit&gt;</strong></p><p>Binary search through commit history to find the commit that introduced a bug. Git checks out the midpoint commit, you test whether the bug is present, you tell Git good or bad, and it narrows down the range. For a regression that could be in any of 200 commits, bisect finds the specific commit in 7-8 steps. This is the command that saves 2 AM debugging sessions.</p><p><strong>git tag -a v2.3.1 -m &quot;Release 2.3.1 - payment timeout fix&quot;</strong></p><p>Annotated tags. Unlike lightweight tags, annotated tags store the tagger’s name, email, date, and message. This is what you use for release tagging. When you need to roll back to the version that was running before the incident, git checkout v2.3.1 is the command you want to run. That only works if you're tagging releases properly.</p><p><strong>git shortlog -sn --since=&quot;30 days ago&quot;</strong></p><p>Summarizes commits by author over a time period. Useful for understanding who’s been shipping what, for release notes, and for the honest-but-uncomfortable question of who might have context on a recent change that’s causing an incident.</p><p><strong>git show &lt;commit-hash&gt;:src/config/database.yml</strong></p><p>Shows the contents of a specific file at a specific commit. When production is misbehaving and you suspect a configuration change, this lets you see exactly what the config looked like at any point in history without checking out the commit. Surgical. Fast. No side effects.</p><h3>The Workflow That Changed How My Teams Ship</h3><p>Commands are tools. They’re only useful if you have a workflow that calls for them.</p><p>Here’s the workflow I’ve implemented on every team I’ve joined since that $47,000 Black Friday incident I wrote about last month. It’s not complicated. It’s just consistent.</p><p><strong>Before starting work:</strong> git fetch --all --prune. Start from a clean view of reality.</p><p><strong>During development:</strong> Small commits with meaningful messages. git commit --fixup for corrections. Named stashes for interruptions.</p><p><strong>Before opening a PR:</strong> git rebase -i to clean up commit history. One logical change per commit. Messages that explain <em>why</em>, not just <em>what</em>.</p><p><strong>During review:</strong> git diff main...feature-branch to understand exactly what's being added. git log --follow for files with history.</p><p><strong>When something breaks:</strong> git bisect to find the commit. git revert to undo it safely. git reflog if something goes wrong with the undo.</p><p><strong>After merging:</strong> git branch --merged main | grep -v main | xargs git branch -d. Clean up. Keep the repository navigable.</p><p><strong>For releases:</strong> Annotated tags. Every time.</p><blockquote><strong><em>If you want all 35 commands in a single reference — organized by workflow, with real-world examples for each — I put them together in one place.</em></strong></blockquote><blockquote><strong><em>→ </em></strong><a href="https://devrimozcay.gumroad.com/l/gmmuu"><strong><em>Master Git in Minutes</em></strong></a><em> — 35 essential commands + real-world workflows, organized the way production engineers actually use them. This is the reference you keep open, not the one you read once and forget.</em></blockquote><h3>Why Most Engineers Never Learn This</h3><p>The honest answer: Git is good enough at 20% functionality to get most things done. The gap between “5 commands” and “35 commands” only becomes visible when something goes wrong.</p><p>And when something goes wrong is not when you want to be learning new commands for the first time.</p><p>The engineers who navigate incidents cleanly, who can trace a bug to a commit in minutes instead of hours, who can deploy a surgical hotfix at midnight without touching unrelated features — they learned these commands before they needed them. In quiet moments. In code reviews. In postmortems where they asked “how could we have caught this faster?”</p><p>The question isn’t whether you’ll need these commands. You will. Every engineer working in production long enough will need all of them eventually.</p><p>The question is whether you’ll know them when that moment arrives.</p><p><em>I write about production engineering, Java, JVM, and what actually breaks in real systems — every week, without the fluff.</em></p><p><a href="https://substack.com/@devrimozcay1"><strong><em>Devrim’s Engineering Notes →</em></strong></a><em> — 1.2K+ engineers already reading.</em></p><p><em>Follow for more on Git, backend engineering, and the tools that separate engineers who ship with confidence from engineers who ship with anxiety.</em></p><img alt="" height="1" src="https://medium.com/_/stat?event=post.clientViewed&amp;referrerSource=full_rss&amp;postId=80745d48b325" width="1" /><hr /><p><a href="https://blog.stackademic.com/stop-using-git-like-a-junior-these-35-commands-will-change-how-your-team-ships-80745d48b325">Stop Using Git Like a Junior.
