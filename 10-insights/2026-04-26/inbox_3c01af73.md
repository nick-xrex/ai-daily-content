<figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*inH4-d_gZZZhhNunh8NWDg.png" /><figcaption>a image which have showing high seq scan and then we did indexing and then valla our query become better</figcaption></figure><p>Alright, let’s get one thing straight. You can write the most elegant, algorithmically perfect Go or Python code on the planet, but if your database has to read a million rows to find one piece of data, your API is going to be slow. And you’ll look like you don’t know what you’re doing.</p><p>Today, we’re diving into the command line to tackle one of the most fundamental performance topics in backend development: <strong>Database Indexing.</strong></p><p>This isn’t a boring theory lecture. We’re going to generate a massive amount of data in PostgreSQL and then make our queries fast. Like, fast.</p><h4>The Setup: Let’s Make a Mess</h4><p>First, you need a PostgreSQL instance. If you don’t have one, just use Docker. I’m not going to teach you how to install Docker; that’s what Google is for. Once you have it, run this command in your terminal.</p><pre># Don't judge my password. You're not my supervisor.<br />docker run --name my-postgres-db -e POSTGRES_PASSWORD=mydirtypassword@hot -d -p 5432:5432 postgres</pre><p>Now, let’s connect to our new database and create a table. We’ll populate it with about 2.5 million products. This should be messy enough.</p><pre>-- Step 1: Connect to the DB<br />-- In a new terminal, run: docker exec -it my-postgres-db psql -U postgres<br /><br />-- Step 2: Create the table<br />CREATE TABLE products (<br />    product_id SERIAL PRIMARY KEY,<br />    category_id INT NOT NULL,<br />    price NUMERIC(10, 2) NOT NULL,<br />    product_name VARCHAR(255) NOT NULL<br />);<br /><br />-- Step 3: Insert 2.5 million rows of glorious, unindexed data<br />INSERT INTO products (category_id, price, product_name)<br />SELECT<br />    5,  <br />    (random() * 99.00)::NUMERIC(10, 2),<br />    'test_product_' || s.id<br />FROM<br />    generate_series(1, 500000) AS s(id);<br /><br />INSERT INTO products (category_id, price, product_name)<br />SELECT<br />    (random() * 500)::INT + 1,<br />    (random() * 2000.00)::NUMERIC(10, 2), <br />    md5(random()::TEXT)<br />FROM<br />    generate_series(1, 2000000);</pre><p>Our battlefield is prepared.</p><h3>Act I: The Slow Query of Despair</h3><p><strong>The Mission:</strong> Your application’s most frequent query is to find products in category_id = 5 that cost less than 100.00. It only needs the product’s name and price.</p><p>Here’s the query:</p><pre>SELECT product_name, price<br />FROM products<br />WHERE category_id = 5<br />  AND price &lt; 100.00;</pre><p>Let’s see how our database handles this. We use the magic command: EXPLAIN ANALYZE.</p><pre>EXPLAIN ANALYZE SELECT product_name, price<br />FROM products<br />WHERE category_id = 5<br />  AND price &lt; 100.00;</pre><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*eKrfdnH0mFNgB6SgTgm-wg.png" /></figure><p>You’ll see something, a <strong>Parallel Sequential Scan</strong>. This is the database’s way of telling you it’s reading the <em>entire damn table</em> to find your data. It’s the equivalent of looking for a single word in a book by reading every page from the beginning.</p><p><strong>The Fix:</strong> We need to give the database an index — a shortcut. Since our query filters on category_id and then on price, let’s create a multi-column index.</p><pre>create index idx_products_larger_category ON products (category_id, price); </pre><p>Now run EXPLAIN ANALYZE again.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*2ug79Eaj7GavoMDQ4tfgnQ.png" /></figure><p>But hold on. Our query only needs product_name and price. The database still has to do a “Heap Scan” to fetch the product_name from the main table. Can we do better?</p><p>Yes. With a <strong>Covering Index</strong>.</p><p>Generated sql</p><pre>-- Drop the old index first<br />drop index idx_products_larger_category;<br /><br />-- Create an index that INCLUDES the data we need<br />create index idx_products_larger_category on products ( category_id, price ) include (product_name);</pre><p>This tells PostgreSQL: “Hey, everything you need for this query is right here in the index itself. Don’t even bother looking at the main table.” Run EXPLAIN ANALYZE one last time.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*1aiaN0WnFOqiSs1Mi5MUYA.png" /></figure><p>You’ll see an <strong>Index Only Scan</strong>. This is the peak form. It’s as fast as it gets for this query.</p><h3>Act II: The “Don’t Break Production” Challenge</h3><p>Okay, so we have our perfect index. But in the real world, you can’t just lock a multi-million-row products table while you build it. That’s how you cause outages and get angry emails from your boss.</p><p><strong>The Mission:</strong> Add the index to the live table without blocking writes (INSERT, UPDATE, DELETE).</p><p><strong>The Fix:</strong> PostgreSQL has a command for this exact scenario. It’s beautiful.</p><pre>-- Drop the old index first<br />drop index idx_products_larger_category;<br /><br />-- Create an index concurrently<br />create index concurrently idx_products_larger_category_inline on products ( category_id, price ) include (product_name);</pre><p>The CONCURRENTLY keyword is your safety net. It tells PostgreSQL to build the index without taking a heavy lock on the table.</p><p><strong>The Trade-offs:</strong></p><ul><li><strong>It’s slower:</strong> A concurrent build takes more time and resources.</li><li><strong>It can fail:</strong> If something goes wrong, you might be left with an “invalid” index that you have to clean up manually (DROP INDEX …).</li><li><strong>The real “production” fix?</strong> Communication. Sometimes the best tool is an email telling your users: “We’re running scheduled maintenance from 2 AM to 3 AM. Things might be a bit weird.” It’s less cool than a zero-downtime command, but often much safer.</li></ul><p>For a deeper dive into how this all works under the hood, the official <a href="https://www.postgresql.org/docs/current/indexes.html"><em>PostgreSQL Documentation on Indexes</em></a> is your best friend. No jokes there, just pure, unadulterated knowledge.</p><p>And that’s it. From a slow query to a production-safe fix. Indexing isn’t magic; it’s just another powerful tool in the backend developer’s arsenal.
