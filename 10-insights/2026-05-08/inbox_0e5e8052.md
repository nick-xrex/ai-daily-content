## I Reviewed 200 Pull Requests Last Year. 80% Had the Same Hidden Time Bomb.

作者基於 200 個 PR 審查經驗，系統性識別出在代碼審查時難以發現但在生產環境中引發故障的「時間炸彈」代碼模式。整體分類顯示 21% 安全（green）、45% 有隱患（yellow）、34% 危險（red）——每三個 PR 就有一個時間炸彈。五大常見模式：(1) 同步外部調用（67 個 PR）—— checkout 端點阻塞等待 email/warehouse/shipping API，正常 1.5 秒、故障時 5+ 秒導致連接池耗盡；(2) 無界限查詢（54 個）—— 無分頁返回數百萬筆記錄（如 847K 筆交易），導致 OOM；(3) 缺失冪等性（41 個）—— 網絡重試造成重複支付/發貨；(4) 不必要鎖（29 個）—— synchronizedMap 序列化所有讀寫，改用 ConcurrentHashMap 一字修復；(5) 級聯故障（18 個）—— message queue 故障致訂單狀態不一致。作者 2023 年因批准有缺陷的庫存系統虧損 $340K，因此系統化記錄每次審查。

### 重點
- 統計數據：一分之一 PR 都是潛在時間炸彈；同步外部調用最常見（67/200），在高並發下（500 個併發 checkout）連接池飢餓導致全系統崩潰
- 無分頁查詢在開發環境（12 筆交易）測不出問題，生產環境 847K+ 筆會直接拉爆記憶體；冪等性缺失在單發測試通過，但行動網絡重試時重複計費
- synchronizedMap vs ConcurrentHashMap 一字之差；級聯故障需設計冗餘（如 queue 下線時 order 已存，不應回滾；event 發送失敗要有降級策略）

The mistake looks harmless in code review. Production disagrees. I review a lot of code. Not because I enjoy gatekeeping. Because three years ago I approved a PR that took down production for six hours. $340K in lost revenue. My name on the approval. After that, I started keeping notes. Every PR I reviewed. Every pattern I saw. Every time something that looked fine in review broke in production. 200 PRs later, the pattern is undeniable. 80% of the dangerous ones had the same characteristic. They worked perfectly. Right up until they didn’t. How I Started Keeping Notes March 2023. Series B startup. 400K users. A developer on my team submitted a PR for a new feature. Inventory reservation system for flash sales. The code was clean. Tests passed. Logic was sound. I approved it in twenty minutes. Two weeks later, flash sale. 12,000 users hit the endpoint simultaneously. Overselling. 847 orders for an item with 200 units in stock. The code worked exactly as written. It just wasn’t written for 12,000 simultaneous users. I went back to the PR. Read every line again. Nothing wrong with any individual line. The problem was invisible at the unit level. It only existed at scale. That’s when I started writing things down. The Pattern Across 200 PRs I categorized every PR I reviewed into three buckets: Green: Safe. Would behave the same at 100 users and 100,000 users. Yellow: Conditional. Fine for now, but has a hidden assumption about load or data volume. Red: Time bomb. Works in testing, breaks in production under real conditions. After 200 PRs: 21% green. 45% yellow. 34% red. One in three PRs I reviewed last year was a time bomb. Not because the developers were bad. Because the time bombs are genuinely hard to see in code review. They look like normal code. They pass tests. They work in staging. They fail in production for reasons that have nothing to do with the code itself. Time Bomb #1: The Synchronous External Call This one appeared in 67 of the 200 PRs. Most common pattern I saw. It looks like this: @PostMapping(&quot;/checkout&quot;) public OrderResponse checkout(@RequestBody CheckoutRequest request) { Order order = orderService.createOrder(request); // Send confirmation email emailService.sendConfirmation(order); // Update inventory in warehouse system warehouseClient.updateInventory(order); // Notify shipping provider shippingClient.notifyOrder(order); return OrderResponse.from(order); } Clean. Readable. Logical sequence of operations. In code review, I see: create order, send email, update warehouse, notify shipping, return response. In production, I see: a checkout endpoint that holds a connection open for the combined latency of three external API calls. Email service: 200–800ms depending on load. Warehouse API: 300–1,200ms. Spikes during their batch jobs. Shipping provider: 150–2,000ms. Degrades badly under load. Normal case: checkout takes 1.5 seconds. Acceptable. Bad case: warehouse API is slow, shipping provider is having a moment. Checkout takes 5 seconds. Users abandon. Worst case: shipping provider times out. Your thread is blocked. Connection pool slot occupied. Multiply by 500 concurrent checkouts. Everything downstream starves. The developer didn’t do anything wrong. They wrote the obvious implementation. The problem is that “obvious implementation” couples your response time to three external services you don’t control. I approved fourteen PRs with this pattern before I realized I was approving the same time bomb over and over. Time Bomb #2: The Unbounded Query Appeared in 54 of the 200 PRs. public List&lt;Transaction&gt; getUserTransactions(Long userId) { return transactionRepository.findByUserId(userId); } Simple. A user wants their transactions. Return their transactions. In development: user has 12 transactions. Returns instantly. In production, two years later: power user has 847,293 transactions. Returns all of them. Serializes all of them to JSON. Sends all of them over the wire. Or worse: someone queries this for a report. All users. All transactions. No pagination. I’ve seen this exact pattern pull 4 million rows into memory and crash a service that had been running fine for 18 months. The developer who wrote it wasn’t thinking about 847,293 transactions. They were thinking about users with 12 transactions. That’s all they’d ever seen. The code is correct. The assumption is wrong. Time Bomb #3: The Missing Idempotency This one took me the longest to start catching. 41 PRs. @PostMapping(&quot;/payment/process&quot;) public PaymentResponse processPayment(@RequestBody PaymentRequest request) { Payment payment = paymentService.charge(request.getUserId(), request.getAmount()); return PaymentResponse.success(payment.getId()); } Looks fine. Process payment, return result. What happens when the network blips between your service and the client? Client sends request. You process payment. You charge the card. Response never reaches client. Client retries. You charge the card again. User gets charged twice. Your support queue fills up. Trust evaporates. This isn’t hypothetical. Mobile networks are unreliable. Load balancers retry. Clients implement retry logic. Requests get duplicated. Any payment endpoint without idempotency handling is a time bomb with a random fuse. I’ve seen this cause double charges. Double shipments. Duplicate account creations. Duplicate notifications sent to 50,000 users. In code review it’s invisible because the happy path works perfectly. There’s no test for “what if this request arrives twice.” Time Bomb #4: The Lock That Didn’t Need to Exist 29 PRs. Similar to what I wrote about in the Marcus incident, but different context. private final Map&lt;String, UserSession&gt; sessionCache = Collections.synchronizedMap(new HashMap&lt;&gt;()); public UserSession getSession(String sessionId) { if (!sessionCache.containsKey(sessionId)) { UserSession session = loadFromDatabase(sessionId); sessionCache.put(sessionId, session); } return sessionCache.get(sessionId); } Developer wanted thread-safe session caching. Used synchronizedMap. Looks reasonable. Problem: synchronizedMap synchronizes individual operations, not compound operations. containsKey → put is not atomic. Two threads can both pass the containsKey check simultaneously. Both load from database. Both put. Race condition. But more importantly: synchronizedMap means every read and write acquires the same lock. At 10,000 concurrent requests, every session lookup queues behind every other session lookup. One global lock. For cache reads. For a session cache that should be the fastest operation in your system. In development: single user, no contention, zero visible impact. In production: 10,000 users, maximum contention, session lookups become a bottleneck that cascades everywhere. The fix is ConcurrentHashMap, which uses segment-level locking and doesn’t serialize all reads. One word change. The time bomb difference. Time Bomb #5: The Cascade Nobody Planned For 18 PRs. The rarest but the most expensive. This one is systemic. It’s not a single piece of code — it’s how multiple pieces interact under failure conditions. Developer adds a feature: when an order is placed, send an event to a message queue. Other services consume that event and do their thing. Looks good. Decoupled architecture. Async processing. Best practices. Nobody designs for: what happens when the queue is down? public Order placeOrder(OrderRequest request) { Order order = orderRepository.save(request.toOrder()); // Publish event eventPublisher.publish(new OrderPlacedEvent(order)); return order; } Queue goes down. eventPublisher.publish() throws an exception. Order was already saved. Exception propagates. Transaction rolls back. Order is deleted. User’s payment was captured. Order doesn’t exist. Or the opposite: exception is swallowed. Order saved. Event never sent. Downstream services never notified. Order sits forever in limbo. Both scenarios happen in production. The code looks correct in isolation. The failure mode only exists at the system level. I missed this pattern for six months before I started asking “what happens to this code when the dependency it calls is unavailable?” What Good Code Review Actually Looks Like After 200 PRs and a lot of expensive lessons, I added five questions to my review process. I don’t ask them for every line. I ask them for every non-trivial piece of logic. Question 1: What’s the worst-case input? Not the test case. Not the happy path. The biggest dataset, the most concurrent users, the edge case that only appears at scale. Question 2: What external systems does this touch? Every external call is a latency dependency. Every external call can fail. Is this call synchronous when it could be async? What happens when it times out? Question 3: Is this idempotent? Can this operation be safely called twice? If not, is there protection against duplicate calls? This matters for any state-changing operation. Question 4: What’s the failure mode? When this code fails — not if, when — what happens to the data? Is it consistent? Is it recoverable? Does it fail loudly or silently? Question 5: Would I be comfortable debugging this at 3 AM? Not whether I understand it now, in daylight, with context. Whether future-me, woken up at 3 AM six months from now, could understand what this code is doing and why it’s failing. These five questions don’t catch everything. But they catch most of the time bombs. The PR That Changed My Approval Process PR 147. August last year. Junior developer. New feature. Clean code. Tests passing. Well-commented. I almost approved it in ten minutes. Question 2 stopped me. What external systems does this touch? The code called an analytics service to log user behavior. Synchronously. In the critical path of the signup flow. Analytics service uptime: 99.2%. That means 0.8% of signups would fail because the analytics call failed. Not because signup was broken. Because analytics was temporarily unavailable. Every signup failure is a user who wanted to join and couldn’t. Every one of those is a potential customer lost. I requested a change: make the analytics call async, don’t block signup on analytics. Developer pushed back: “Analytics needs to be real-time.” Me: “Is real-time analytics worth losing 0.8% of signups?” They thought about it. Changed it to async. Three months later, the analytics service had a 4-hour outage. Signups continued uninterrupted. Nobody noticed except the analytics team. Without that change, 4 hours of signup failures. In Q4. Before a marketing campaign. What I Tell Junior Developers Now When someone on my team submits their first PR, I tell them the same thing. Code review is not about catching bugs. Unit tests catch bugs. Integration tests catch bugs. QA catches bugs. Code review is about catching assumptions. Every piece of code embeds assumptions. About data volume. About call frequency. About external reliability. About failure modes. About who else is calling this function at the same time. In development, most assumptions are correct. Data volumes are small. Load is low. External services are healthy. You’re the only one running the code. Production invalidates assumptions. Your job in code review is to find the assumptions and ask: what happens when this assumption is wrong? Most time bombs aren’t bugs. They’re correct code with wrong assumptions. The difference between a senior engineer and a junior engineer isn’t that the senior writes better code. It’s that the senior has been wrong about assumptions before. And remembers what it cost. The Spring Boot Production Checklist grew out of exactly this kind of pattern recognition — 47 checks that catch the assumptions most code reviews miss. Not theory. The actual things that slip through and break at 3 AM. Because the time bomb in PR 73 looks identical to the time bomb in PR 147. Until production tells you otherwise. Every week I write about the patterns that survive code review and break in production.
