## Understanding Expose an API, API Permissions, and App Roles in Azure Entra ID

<p>When registering applications in Azure Entra ID, three configuration surfaces appear repeatedly — Expose an API, API Permissions, and App Roles. They are located on different blades, configured on different applications, and serve different purposes, yet they form a single authorization pipeline. Misunderstanding any one of them leads directly to broken token flows, missing claims, and confusing error messages such as “Either scp or roles claim need to be present in the token.”</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*-o2YlsUEabs7rV-mwvpL1Q.png" /></figure><p>This article builds a clear mental model of how these three concepts relate. The organizing principle is <strong>definition → request → enforcement</strong>: the backend API defines what permissions exist, the client application requests a subset of those permissions, and Azure Entra ID issues a token whose claims the API then enforces. Every portal setting, manifest field, and token claim maps to one of those three stages.</p><h3>The Core Model: Two Applications, One Permission Flow</h3><p>Every protected-API scenario involves at least two app registrations:</p><pre>+---------------------------+          +---------------------------+<br />|   CLIENT APPLICATION      |          |   BACKEND API             |<br />|   (frontend / daemon)     |          |   (resource server)       |<br />|                           |          |                           |<br />|  Configured here:         |          |  Configured here:         |<br />|  - API Permissions        |          |  - Expose an API (scopes) |<br />|    (what I want to call)  |          |  - App Roles              |<br />|                           |          |  - Application ID URI     |<br />+---------------------------+          +---------------------------+<br />            |                                      |<br />            |    1. Client requests token          |<br />            +-------------------------------------&gt;|<br />            |                                      |<br />            |    2. Azure issues token             |<br />            |&lt;-------------------------------------+<br />            |                                      |<br />            |    3. Client calls API with token    |<br />            +-------------------------------------&gt;|<br />            |                                      |<br />            |    4. API validates token claims     |<br />            |                                      |</pre><p>The client application never defines the permissions it receives. It only declares which permissions it intends to request. The backend API is the sole authority on what permissions exist. Azure Entra ID sits between the two, evaluating consent and assignment, then encoding the result into a JWT access token.</p><h3>1. Expose an API — Defining What the Backend Offers</h3><p>Expose an API is configured exclusively on the backend API’s app registration. It answers one question: <strong>What permissions does my API support?</strong></p><p>This blade contains three important elements:</p><h4>1.1 Application ID URI</h4><p>This is the unique identifier for your API within the tenant. It typically takes the form:</p><pre>api://&lt;CLIENT_ID&gt;</pre><p>When any client requests a token for your API, it references this URI. The Application ID URI is the aud (audience) claim in the resulting access token - it tells the API &quot;this token was issued for you.&quot;</p><h4>1.2 Delegated Permission Scopes</h4><p>Scopes are the delegated permissions your API offers. Each scope represents a specific unit of access that a signed-in user can consent to. The key characteristic of a delegated scope is that it requires a user context — the application acts on behalf of the user.</p><p>When you define a scope such as:</p><pre>Value: Mcp.Tools.ReadWrite<br />Type: User</pre><p>you are declaring that clients may request this permission on behalf of users. If the user (or an admin) consents, the resulting token will contain the permission in the scp claim:</p><pre>{<br />  &quot;aud&quot;: &quot;api://&lt;CLIENT_ID&gt;&quot;,<br />  &quot;scp&quot;: &quot;Mcp.Tools.ReadWrite&quot;<br />}</pre><p>The scp claim is a space-delimited string. If the user has consented to multiple scopes, they appear together:</p><pre>&quot;scp&quot;: &quot;Mcp.Tools.Read Mcp.Tools.ReadWrite&quot;</pre><h4>1.3 Pre-Authorized Applications</h4><p>Optionally, you can pre-authorize specific client applications so that their users are not prompted for consent. This is useful for first-party clients that you trust completely. In the manifest, this appears under api.preAuthorizedApplications, listing client app IDs and the scope IDs they are pre-authorized for.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*HuJrndLlp_EWvZNyMzJc4Q.png" /></figure><blockquote><strong><em>Portal location:</em></strong><em> Azure Portal → App Registrations → [Backend API] → Expose an API</em></blockquote><blockquote><em>This blade shows the Application ID URI at the top, followed by a list of defined scopes (with their values, types, and consent descriptions), and the Pre-authorized applications section at the bottom. Each scope entry displays its full URI in the format </em><em>api://&lt;CLIENT_ID&gt;/&lt;scope_value&gt;.</em></blockquote><h3>2. API Permissions — Declaring What the Client Wants</h3><p>API Permissions is configured on the <strong>client</strong> application’s app registration. It answers: <strong>Which APIs does my app intend to call, and what level of access does it need?</strong></p><p>This is the consumer side of the contract. The client cannot invent permissions — it can only reference permissions that an API has already defined.</p><h4>2.1 Two Types of API Permissions</h4><p>When you add an API permission, you choose between two categories:</p><pre>+------------------+------------------------------+-------------+-----------------------------------+<br />| Permission Type  | When to Use                  | Token Claim | Requires                          |<br />+------------------+------------------------------+-------------+-----------------------------------+<br />| Delegated        | A user is signed in; the app | scp         | User or admin consent             |<br />|                  | acts on behalf of the user   |             |                                   |<br />+------------------+------------------------------+-------------+-----------------------------------+<br />| Application      | No user is present; the app  | roles       | Admin consent + role assignment   |<br />|                  | acts as itself (daemon/svc)  |             |                                   |<br />+------------------+------------------------------+-------------+-----------------------------------+</pre><p>Delegated permissions reference the scopes defined under “Expose an API” on the target API. Application permissions map to app roles for custom APIs but may be exposed differently for Microsoft APIs while still resulting in roles claims. (discussed in the next section).</p><h4>2.2 What API Permissions Actually Do</h4><p>Configuring an API permission on a client app does <strong>not</strong> automatically grant access. It declares intent. The permission still requires either:</p><ul><li>User consent or admin consent (for delegated permissions), or</li><li>Admin consent and role assignment (for application permissions).</li></ul><p>Until consent or assignment is completed, the permission exists only as a declared requirement in the client’s manifest under requiredResourceAccess.</p><h4>2.3 A Common Source of Confusion</h4><p>Many developers configure API Permissions on the wrong application. The rule is simple:</p><pre>Expose an API   = configured on the API    (the app being called)<br />API Permissions = configured on the client (the app making the call)</pre><p>If you find yourself adding an “Expose an API” scope on your frontend SPA, or adding “API Permissions” on your backend API to reference itself, you have likely reversed the roles.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*V5w34A_SFtbjVkLTAEy64A.png" /></figure><blockquote><strong><em>Portal location:</em></strong><em> Azure Portal → App Registrations → [Frontend Client] → API Permissions</em></blockquote><blockquote><em>This blade lists all APIs the client has declared intent to call. Each entry shows the API name, the specific permission name, its type (Delegated or Application), and the current consent status. An “Add a permission” button opens a panel where you can browse “My APIs,” “Microsoft APIs,” or enter a custom API. After selecting an API, a toggle allows switching between “Delegated permissions” (showing the scopes from that API’s Expose an API blade) and “Application permissions” (showing the app roles defined on that API).</em></blockquote><h3>3. App Roles — Role-Based Authorization and Application-Only Access</h3><p>App Roles are defined on the backend API’s app registration (under the “App roles” blade or directly in the manifest). They serve two distinct purposes:</p><ol><li><strong>Role-based authorization for users</strong> — assigning roles like “Admin” or “Reader” to specific users or groups.</li><li><strong>Application-only access</strong> — granting service principals permission to call the API without any user present.</li></ol><h4>3.1 How App Roles Differ from Scopes</h4><p>This is the most critical distinction in the entire authorization model:</p><pre>+------------------------+---------------------------+---------------------------+<br />| Characteristic         | Delegated Scopes          | App Roles                 |<br />|                        | (Expose an API)           |                           |<br />+------------------------+---------------------------+---------------------------+<br />| Defined on             | Backend API               | Backend API               |<br />+------------------------+---------------------------+---------------------------+<br />| Used by                | Signed-in users           | Users, groups, or apps    |<br />|                        | (via client)              |                           |<br />+------------------------+---------------------------+---------------------------+<br />| How access is granted  | User or admin consent     | Explicit assignment       |<br />|                        |                           | by admin                  |<br />+------------------------+---------------------------+---------------------------+<br />| Token claim            | scp (space-delimited)     | roles (JSON array)        |<br />+------------------------+---------------------------+---------------------------+<br />| Works without a user   | No                        | Yes (when assigned to     |<br />|                        |                           | an application)           |<br />+------------------------+---------------------------+---------------------------+<br />| Consent mechanism      | Consent prompt or         | Role assignment via       |<br />|                        | admin grant               | Enterprise Application    |<br />+------------------------+---------------------------+---------------------------+</pre><p>An app role defined with allowedMemberTypes: [&quot;Application&quot;] can be assigned to service principals, enabling the client credentials (app-only) flow. An app role defined with allowedMemberTypes: [&quot;User&quot;] can be assigned to users and groups. If both member types are included, the role supports both scenarios.</p><p>When a user or application has been assigned a role, the token contains:</p><pre>{<br />  &quot;aud&quot;: &quot;api://&lt;CLIENT_ID&gt;&quot;,<br />  &quot;roles&quot;: [&quot;Mcp.Tools.ReadWrite.All&quot;]<br />}</pre><p>A user token can contain both scp and roles simultaneously if the user has consented scopes and has also been assigned app roles. An application-only token will contain only roles - never scp, because there is no user to delegate from.</p><h4>3.2 The Critical Gap: Definition vs Assignment</h4><p>This is the single most common mistake developers encounter with app roles.</p><p><strong>Defining a role is not the same as assigning it.</strong> When you create an app role in the backend’s App Registration, you have only declared that the role exists. No user or application receives it automatically. Until you perform explicit assignment, the roles claim will not appear in any token.</p><p>The assignment happens in a <strong>different location</strong> from the definition:</p><pre>Definition:   App Registration → App roles blade<br />Assignment    Enterprise Applications → [Your API]<br />(users/grps): → Users and groups → Add assignment<br />               → select user → select role<br />Assignment    Grant application permission in the client's<br />(app):        API Permissions blade → Admin consent</pre><p>When you visit the Enterprise Application’s “Users and groups” page and see a user listed with “Default Access,” that does <strong>not</strong> mean the user has been assigned any app role. “Default Access” simply means the user can sign in — it carries no role claim. You must explicitly add the user with a specific role for the roles claim to appear in their token.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*Sa2uXqjp9mV69pCI46o2lw.png" /></figure><blockquote><strong><em>Portal location (App roles blade):</em></strong><em> Azure Portal → App Registrations → [Backend API] → App roles</em></blockquote><blockquote><em>This blade lists all defined app roles. Each row shows the display name, value (the string that appears in the token), allowed member types (Users/Groups, Applications, or Both), and a description. Roles can be enabled or disabled without deleting them. This is the </em>definition<em> surface only — no assignments are made here.</em></blockquote><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*UzoNHby-ELCfBkzVBFNwFw.png" /></figure><blockquote><strong><em>Portal location (Assignment):</em></strong><em> Azure Portal → Enterprise Applications → [Backend API] → Users and groups</em></blockquote><blockquote><em>This page is where actual access is granted. It shows two distinct states you will encounter: a user or service principal listed with “Default Access” (meaning they can sign in but have no role assigned, so no </em><em>roles claim will appear in their token), versus a user or service principal listed with a specific role name (e.g., &quot;</em>Mcp.Tools.ReadWrite<em>.All&quot;), which means the </em><em>roles claim will be present. The distinction between these two states is the single most common source of &quot;missing roles claim&quot; bugs.</em></blockquote><blockquote><em>To assign a role, click “Add user/group,” select the identity, then select the specific role from the dropdown. The role dropdown will only show roles that have been defined in the App Registration’s App roles blade with the appropriate </em><em>allowedMemberTypes.</em></blockquote><h3>4. How the Three Concepts Work Together: End-to-End Token Flow</h3><p>The following diagram traces the complete lifecycle from configuration to token validation:</p><pre>CONFIGURATION PHASE<br />====================<br />Backend API App Registration:<br />  +-- Expose an API<br />  |     Application ID URI: api://&lt;CLIENT_ID&gt;<br />  |     Scope: Mcp.Tools.ReadWrite (delegated, type: User)<br />  |<br />  +-- App Roles<br />        Role: Mcp.Tools.ReadWrite.All (allowedMemberTypes: User, Application)<br />Client App Registration:<br />  +-- API Permissions<br />        Delegated:    Mcp.Tools.ReadWrite     (references backend scope)<br />        Application:  Mcp.Tools.ReadWrite.All (references backend app role)<br />Enterprise Application (Backend API):<br />  +-- Users and Groups<br />        User &quot;alice@contoso.com&quot;          → assigned role: Mcp.Tools.ReadWrite.All<br />        Service Principal &quot;batch-processor&quot; → assigned role: Mcp.Tools.ReadWrite.All<br /><br />RUNTIME PHASE (User Flow)<br />==========================<br />1. Azure issues token:<br />     {<br />       &quot;aud&quot;: &quot;api://&lt;CLIENT_ID&gt;&quot;,<br />       &quot;scp&quot;: &quot;Mcp.Tools.ReadWrite&quot;,<br />       &quot;roles&quot;: [&quot;Mcp.Tools.ReadWrite.All&quot;]<br />     }<br />5. Client sends token to API<br />6. API validates: aud, signature, expiry, scp and/or roles<br /><br />RUNTIME PHASE (App-Only Flow)<br />==============================<br />1. Service principal authenticates using client credentials<br />2. Client requests: scope = api://&lt;CLIENT_ID&gt;/.default<br />3. Azure issues token:<br />     {<br />       &quot;aud&quot;: &quot;api://&lt;CLIENT_ID&gt;&quot;,<br />       &quot;roles&quot;: [&quot;Mcp.Tools.ReadWrite.All&quot;]<br />     }<br />     (no &quot;scp&quot; claim - no user present)<br />5. Client sends token to API<br />6. API validates: aud, signature, expiry, roles</pre><h4>4.1 The .default Scope</h4><p>When a service principal requests a token using client credentials, .default resolves to all statically configured and consented application permissions for that resource, not dynamically selectable scopes. Instead, it uses the special meta-scope:</p><pre>api://&lt;CLIENT_ID&gt;/.default</pre><p>This instructs Azure Entra ID to look up all app role assignments for that service principal on the target API and include them in the roles claim. The .default scope does <strong>not</strong> grant &quot;all permissions&quot; - it grants only the roles that have been explicitly assigned to that calling principal.</p><p>For user flows, the az account get-access-token --resource command and MSAL's acquireTokenSilent both effectively request all consented delegated scopes for the target resource, which is why scp may appear even when you did not explicitly pass a scope parameter.</p><h4>4.2 Why SPN Tokens Never Contain scp</h4><p>A service principal authenticating via client credentials has no user context. Delegated scopes are, by definition, permissions exercised on behalf of a user. With no user present, there is no delegation, and therefore no scp claim. Azure Entra ID enforces this strictly - even if the service principal's app registration has delegated permissions configured under API Permissions, the client credentials token will contain only roles.</p><h3>5. Token Claim Reference</h3><p>The following table summarizes what each token claim means and where its value originates:</p><pre>+---------+-------------------------------------------+----------------------------------------------+<br />| Claim   | Meaning                                   | Source                                       |<br />+---------+-------------------------------------------+----------------------------------------------+<br />| aud     | Intended audience - identifies target API | Application ID URI from &quot;Expose an API&quot;      |<br />+---------+-------------------------------------------+----------------------------------------------+<br />| appid   | Client app that requested the token       | Client app's App (client) ID                 |<br />+---------+-------------------------------------------+----------------------------------------------+<br />| scp     | Delegated permissions granted to the user | Scopes from &quot;Expose an API,&quot; filtered by     |<br />|         |                                           | consent                                      |<br />+---------+-------------------------------------------+----------------------------------------------+<br />| roles   | App roles assigned to calling identity    | App Roles from API, filtered by assignment   |<br />+---------+-------------------------------------------+----------------------------------------------+<br />| oid     | Object ID of the signed-in user           | Azure AD user directory                      |<br />+---------+-------------------------------------------+----------------------------------------------+<br />| tid     | Tenant ID                                 | Azure AD tenant                              |<br />+---------+-------------------------------------------+----------------------------------------------+</pre><p>A token with scp present indicates a delegated (user) flow. A token with only roles and no scp indicates an application-only flow. A token can contain both if a signed-in user also has assigned app roles.</p><blockquote><strong><em>Decoding tokens:</em></strong><em> Navigate to </em><a href="https://jwt.ms"><em>https://jwt.ms</em></a><em> and paste an access token to inspect its claims. The decoded view will show all claims including </em><em>aud, </em><em>appid, </em><em>scp, and </em><em>roles. Comparing a user token (which will contain </em><em>scp) side-by-side with an app-only token (which will contain only </em><em>roles) makes the difference immediately visible.</em></blockquote><h3>6. Common Misconceptions and Failure Cases</h3><h4>6.1 “I defined the role, but it does not appear in the token”</h4><p>This is the most frequent issue. The role exists in the App Registration manifest but has not been assigned via Enterprise Applications. Navigate to <strong>Enterprise Applications → your API → Users and groups</strong> and verify that the identity (user or service principal) is listed with the correct role — not just “Default Access.”</p><h4>6.2 “I configured API Permissions but still get an error”</h4><p>Adding an API Permission to a client app only declares intent. For delegated permissions, the user or an admin must still consent. For application permissions (app roles), an admin must grant tenant-wide consent. Without that consent step, the token request will fail or return a token without the expected claims.</p><h4>6.3 “I set up Expose an API on my frontend app”</h4><p>The frontend client does not typically need to expose an API. It is a consumer, not a provider. Expose an API should be configured on the backend (the app that receives and validates tokens). The frontend only needs API Permissions pointing to the backend’s scopes.</p><h4>6.4 “My SPN requested a specific scope but got no scp claim&quot;</h4><p>Service principals using client credentials cannot receive delegated scopes. The scp claim is reserved for user-delegated flows. For application-only access, define an app role on the API, assign it to the service principal, and use api://&lt;CLIENT_ID&gt;/.default as the scope parameter. The resulting token will contain roles instead of scp.</p><h4>6.5 Confusing the “Expose an API” blade with the “API Permissions” blade</h4><p>These blades look similar and both deal with permissions, but they serve opposite sides of the contract:</p><pre>Expose an API   →  &quot;I am an API, and here is what I offer&quot;<br />API Permissions →  &quot;I am a client, and here is what I need&quot;</pre><p>If you configure them on the wrong application, your token flow will not work.</p><h3>7. When to Use Scopes, When to Use App Roles, and When to Use Both</h3><p>The choice between scopes and roles is not binary. They address different authorization patterns and can coexist on the same API.</p><p><strong>Use Delegated Scopes When:</strong></p><ul><li>The API is always called on behalf of a signed-in user</li><li>You want the user to consent to specific permissions</li><li>You need fine-grained, per-action permissions (e.g., Tasks.Read, Tasks.Write, Tasks.Delete)</li><li>The API should enforce data access boundaries per user (the user can only see their own data)</li></ul><p><strong>Use App Roles When:</strong></p><ul><li>A daemon, background job, or service needs to call the API without any user</li><li>You want an admin to explicitly assign access levels (e.g., Admin, Reader, Contributor) rather than relying on consent</li><li>You need role-based access control where different users see different features</li><li>You want to model application-level permissions that are broader than individual user consent</li></ul><p><strong>Use Both When:</strong></p><ul><li>Your API supports interactive user access and background service access</li><li>You want fine-grained user-level scopes for normal operations plus broader role-based permissions for administrative functions</li><li>Example: define scopes Tasks.Read and Tasks.Write for end users, and an app role Tasks.ManageAll for admins and service accounts</li></ul><p>In this combined model, the API’s validation logic should check for either scp or roles depending on the endpoint's requirements:</p><pre>def authorize(claims, required_scope=None, required_role=None):<br />    &quot;&quot;&quot;<br />    Validates that the token contains the required scope or role.<br />    Supports both user-delegated and app-only flows.<br />    &quot;&quot;&quot;<br />    if claims.get(&quot;aud&quot;) != &quot;api://&lt;CLIENT_ID&gt;&quot;:<br />        return &quot;Rejected: wrong audience&quot;<br />    scp   = claims.get(&quot;scp&quot;, &quot;&quot;)<br />    roles = claims.get(&quot;roles&quot;, [])<br />    if required_scope and required_scope in scp.split():<br />        return &quot;Authorized via delegated scope&quot;<br />    if required_role and required_role in roles:<br />        return &quot;Authorized via app role&quot;<br />    return &quot;Rejected: insufficient permissions&quot;</pre><p>Example call — user flow:</p><pre>user_claims = {<br />    &quot;aud&quot;:   &quot;api://&lt;CLIENT_ID&gt;&quot;,<br />    &quot;scp&quot;:   &quot;Mcp.Tools.ReadWrite Mcp.Tools.Read&quot;,<br />    &quot;roles&quot;: []<br />}<br />print(authorize(user_claims, required_scope=&quot;Mcp.Tools.Read&quot;))<br /># Output: Authorized via delegated scope</pre><p>Example call — app-only flow:</p><pre>app_claims = {<br />    &quot;aud&quot;:   &quot;api://&lt;CLIENT_ID&gt;&quot;,<br />    &quot;scp&quot;:   &quot;&quot;,<br />    &quot;roles&quot;: [&quot;Mcp.Tools.ReadWrite.All&quot;]<br />}<br />print(authorize(app_claims, required_role=&quot;Mcp.Tools.ReadWrite.All&quot;))<br /># Output: Authorized via app role</pre><h3>8. The Consent and Assignment Model</h3><p>Scopes and roles follow fundamentally different paths to reach the token:</p><pre>DELEGATED SCOPES PATH<br />======================<br />API defines scope (Expose an API)<br />        |<br />Client declares permission (API Permissions - Delegated)<br />        |<br />User or admin consents<br />        |<br />Azure includes scope in &quot;scp&quot; claim<br /><br />APP ROLES PATH<br />===============<br />API defines role (App Roles)<br />        |<br />Client declares permission (API Permissions - Application)<br />        |<br />Admin grants consent<br />        |<br />Admin assigns role (Enterprise App → Users and Groups)<br />        |<br />Azure includes role in &quot;roles&quot; claim</pre><p>Note the additional step for app roles: <strong>assignment</strong>. Consent alone is insufficient — the role must be explicitly assigned to the specific user or service principal. This is the step that catches most developers off guard.</p><h3>9. Tradeoffs and Design Considerations</h3><p><strong>Scopes Offer Flexibility but Less Control</strong></p><p>Delegated scopes integrate with Azure’s consent framework, which means users can consent to permissions themselves (unless admin consent is required). This is convenient for broad adoption but provides less centralized control — any user who consents will receive the scope in their token.</p><p><em>Tradeoff: easier onboarding, less admin oversight.</em></p><p><strong>App Roles Offer Control but Require More Administration</strong></p><p>App roles require an admin to explicitly assign each user or application. This provides precise control over who gets what access, but it introduces an operational burden: every new user or service must be individually assigned.</p><p><em>Tradeoff: tighter security, more manual administration.</em></p><p><strong>Combined Approach Maximizes Coverage but Increases Validation Complexity</strong></p><p>Supporting both scopes and roles means the API must inspect multiple token claims and implement branching logic. The validation code must handle tokens that contain scp only, roles only, or both. This is manageable with proper middleware, but it does increase the surface area for authorization bugs.</p><p><em>Tradeoff: maximum flexibility, higher implementation complexity.</em></p><h3>10. Rebuilding This Setup from Documentation</h3><p>When you need to recreate this architecture from scratch, follow this sequence:</p><p><strong>Step 1 — Create the Backend API App Registration</strong></p><ul><li>Set the Application ID URI (e.g., api://&lt;CLIENT_ID&gt;)</li><li>Under “Expose an API,” add delegated scopes for user-facing operations</li><li>Under “App roles,” define roles for role-based or application-only access</li><li>Set allowedMemberTypes appropriately: [&quot;User&quot;] for user roles, [&quot;Application&quot;] for service-to-service, or both</li></ul><p><strong>Step 2 — Create the Client App Registration</strong></p><ul><li>Configure the appropriate redirect URI (SPA, web, or public client)</li><li>Under “API Permissions,” add delegated permissions referencing the backend’s scopes</li><li>If the client also needs app-only access, add application permissions referencing the backend’s roles</li><li>Grant admin consent if required</li></ul><p><strong>Step 3 — Assign Roles (When Using App Roles)</strong></p><ul><li>Navigate to <strong>Enterprise Applications → [Backend API] → Users and groups</strong></li><li>Assign users to specific roles for user-based role access</li><li>For service principals, grant the application permission and provide admin consent</li></ul><p><strong>Step 4 — Implement Token Validation in the API</strong></p><ul><li>Validate the aud claim matches your Application ID URI</li><li>For user calls: check the scp claim for required delegated permissions</li><li>For app-only calls: check the roles claim for required app roles</li><li>Validate token signature, issuer, and expiry using standard JWT libraries</li><li>Perform validation on every request — HTTP is stateless</li></ul><h3>Mental Checklist for Designing or Debugging Your Setup</h3><p>Use this checklist when creating a new setup or troubleshooting an existing one:</p><p><strong>Definition (Backend API)</strong></p><ul><li>Is an Application ID URI set?</li><li>Are delegated scopes defined under “Expose an API” for user-facing access?</li><li>Are app roles defined for role-based or app-only access?</li><li>Do app roles have the correct allowedMemberTypes (User, Application, or both)?</li></ul><p><strong>Request (Client App)</strong></p><ul><li>Does the client’s “API Permissions” reference the correct backend API?</li><li>Are delegated permissions listed for user-flow scopes?</li><li>Are application permissions listed for app-only roles?</li><li>Has admin consent been granted where required?</li></ul><p><strong>Assignment (Enterprise Applications)</strong></p><ul><li>For user roles: is each user assigned the correct role (not just “Default Access”)?</li><li>For service principal roles: is the service principal assigned the correct role on the API’s enterprise application?</li></ul><p><strong>Token Verification</strong></p><ul><li>Does the token’s aud match the API's Application ID URI?</li><li>For user tokens: does scp contain the expected scope?</li><li>For app-only tokens: does roles contain the expected role?</li><li>Is the token being validated on every API request, not just once?</li></ul><p><strong>Failure Diagnosis</strong></p><ul><li>If scp is missing: is the user signed in? Did the client request the scope? Was consent granted?</li><li>If roles is missing: was the role assigned (not just defined)? Is the assignment on the correct enterprise application? Was a new token requested after assignment?</li><li>If the error says “Admin consent required”: does the permission require admin consent? Has the admin granted it?</li></ul><p>This model — definition on the API, request on the client, enforcement via token claims — is the foundation of every Azure Entra ID authorization design. Once you internalize this structure, you can navigate any combination of scopes, roles, user flows, and app-only flows without confusion.</p><h3>A message from our Founder</h3><p>Hey, <a href="https://linkedin.com/in/sunilsandhu">Sunil</a> here.
