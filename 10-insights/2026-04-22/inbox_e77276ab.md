## I Built an AWS Bot That Auto-Posts My Poetry to Instagram Every Day

<h4>A weekend project using AWS CDK, Lambda, and the Instagram Graph API — and all the traps I fell into along the way.</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*lxUyuVTxcBeQEzj2iDaVVA.jpeg" /><figcaption>Photo on <a href="https://pixabay.com/users/jarmoluk-143740/">jarmoluk</a></figcaption></figure><p>I write poetry. Over the years, I’ve accumulated a stack of poems sitting in a spreadsheet, doing nothing. Meanwhile, I also take a lot of photos on my iPhone that never leave the camera roll.</p><p>One weekend I thought: <em>what if a bot just posted one of my poems to Instagram every day, paired with one of my photos, without me lifting a finger?</em></p><p>A few hours later, I had it running on AWS. This is the story of how — and more importantly, all the things that broke along the way.</p><h3>What It Does</h3><p>Once a day at 9 PM, the bot:</p><ol><li>Pulls the poem with the lowest posted_count from DynamoDB</li><li>Grabs the oldest photo waiting in the S3 /pending folder</li><li>Resizes and compresses it to meet Instagram’s requirements</li><li>Serves the image via CloudFront</li><li>Publishes it to Instagram through the Graph API</li><li>Moves the photo to /posted and increments the poem's post count</li></ol><p>That’s it. I drop photos into S3 whenever I feel like it. The bot handles the rest.</p><h3>The Architecture</h3><p>EventBridge fires a scheduled event every day at 9 PM. That triggers a Lambda function, which talks to DynamoDB, S3, CloudFront, and the Instagram Graph API. Secrets live in Systems Manager Parameter Store. The whole stack is defined in AWS CDK (TypeScript), with the Lambda code in Python.</p><p>The key design choice: <strong>S3 stays private</strong>. CloudFront sits in front of it and serves images publicly to Instagram. This matters a lot, as you’ll see below.</p><h3>Before</h3><p>Everything up to here is the setup. Below the line, I’m writing up the actual implementation: the full walkthrough, every trap I hit, and how I got out of each one.</p><p>The traps are the real value. If you’re planning to build anything that posts to Instagram via the Graph API, you’ll almost certainly run into at least a few of these:</p><ul><li>Why Instagram rejects your image URL even when it works in a browser</li><li>Why your image gets “downloaded” instead of displayed (and why Instagram hates this)</li><li>How to deal with Pillow on Lambda when you can’t just pip install it locally</li><li>The two-step async dance that the Instagram API forces you into</li></ul><p>If you’ve ever stared at &quot;Only photo or video can be accepted as media type&quot; wondering what on earth that means — this article is for you.</p><h3>Step 1: Initialize the CDK Project</h3><p>AWS CDK (Cloud Development Kit) lets you define infrastructure in TypeScript. You write code, run cdk deploy, and CDK generates a CloudFormation template behind the scenes and provisions everything for you.</p><p>Compared to writing CloudFormation YAML by hand, CDK feels like magic — it resolves dependencies, wires up IAM roles automatically, and keeps your infrastructure and your application code in the same repo.</p><p>Initialize the project, bootstrap your AWS account/region for CDK, and you’re ready to start defining resources.</p><h3>Step 2: The S3 Bucket</h3><p>The bucket has two logical folders: /pending (photos waiting to be posted) and /posted (photos that have already been used).</p><p>S3 doesn’t actually have folders — they’re just key prefixes. I create .keep placeholder files in each so they show up in the console.</p><p><strong>Critical settings:</strong></p><ul><li>BlockPublicAccess: BLOCK_ALL — the bucket stays fully private</li><li>RemovalPolicy: RETAIN — so cdk destroy doesn't nuke my photos</li></ul><p>I’ll connect to this bucket from my iPhone using Owlfiles, an app that can mount S3 directly. Dragging a photo into the /pending folder is all the manual work I need to do.</p><h3>Step 3: The DynamoDB Table for Poems</h3><p>The schema is minimal:</p><ul><li>poem_id (partition key) — a UUID</li><li>title — the poem's title</li><li>body — the poem text</li><li>posted_count — how many times it's been posted</li></ul><p>I add a Global Secondary Index on posted_count so I can efficiently query &quot;the poem that's been posted the least.&quot; The GSI needs a partition key, so I use a constant dummy value (&quot;poem&quot;) across all items. A small hack, but it works.</p><h3>Step 4: Import Poems from CSV</h3><p>I’d written all my poems as drafts on Japan’s <em>note</em> platform and exported them as CSV. The CSV had a bunch of things I <em>didn’t</em> want imported — essays, fiction, table-of-contents pages — and most poems had pre-ambles and after-words wrapped around the actual poem body.</p><p>I wrote a small Python script using boto3 and pandas to:</p><ol><li>Filter out rows whose title contained “essay,” “fiction,” or “sitemap”</li><li>Detect the -------- dividers I commonly use in note posts, and extract only the middle (the poem itself)</li><li>Skip any row with an empty body</li><li>put_item each remaining poem into DynamoDB with posted_count: 0</li></ol><p>Out of 113 rows, 101 made it through the filter. All of them landed in DynamoDB with posted_count: 0, ready to be chosen.</p><h3>Step 5: The CloudFront Distribution (This Is Where Things Got Real)</h3><p>My first attempt was to generate a pre-signed S3 URL in Lambda and hand it to Instagram. Clean, simple, no public bucket needed.</p><p>Instagram’s response:</p><blockquote>“Only photo or video can be accepted as media type.”</blockquote><p>After a lot of squinting at the docs, I learned that <strong>Instagram’s crawler refuses URLs with query-string auth tokens or redirects</strong>. Pre-signed URLs are dense with exactly those. Google Drive “direct download” links fail for the same reason. Instagram wants a clean, static, public URL pointing at the raw bytes.</p><p>The fix: keep the bucket private, put CloudFront in front of it with Origin Access Control, and hand Instagram the CloudFront URL instead. Clean URL, no auth, no redirects, works every time.</p><p>CDK makes this a few lines. The important settings are HTTPS_ONLY for the viewer protocol and withOriginAccessControl to wire up the OAC between CloudFront and S3.</p><h3>Step 6: Build a Pillow Layer for Lambda</h3><p>To resize images, I needed Pillow. Lambda doesn’t include it by default, so you need a Lambda layer.</p><p>The catch: <strong>Pillow has native binaries</strong>. If you pip install it on your laptop, those binaries are built for your OS and Python version, not Lambda's. The import will fail silently (or very loudly) in production.</p><p>The cleanest solution is to build the layer inside AWS CloudShell, because CloudShell’s Linux environment matches Lambda’s closely enough. The key pip flags are:</p><ul><li>--platform manylinux2014_x86_64 — target Lambda's architecture</li><li>--python-version 3.12 — target the runtime you'll use</li><li>--only-binary=:all: — force pip to use the pre-built wheel</li></ul><p>Package the result as a zip, publish it as a layer with aws lambda publish-layer-version, and reference the layer ARN in your CDK stack. Done.</p><h3>Step 7: The Lambda Function</h3><p>This is where everything converges. The function does six things in order:</p><p><strong>1. Fetch the least-posted poem.</strong> One DynamoDB GSI query, ScanIndexForward: True, Limit: 1. Boring and fast.</p><p><strong>2. List </strong><strong>/pending in S3.</strong> If nothing's there (ignoring the .keep placeholder), the function returns early — no photo, no post. I originally planned to fall back on Bedrock to generate an image, but decided that &quot;skip today&quot; is simpler and honest.</p><p><strong>3. Resize and compress the image.</strong> Instagram’s ceiling is 8MB per image. My iPhone 16 photos are routinely 15–17MB. Using Pillow:</p><ul><li>Apply ImageOps.exif_transpose first — otherwise portrait photos end up sideways</li><li>Convert to RGB (some images come in as RGBA or CMYK, which Instagram hates)</li><li>Resize so the longest side is at most 1440px (Instagram’s max)</li><li>Save as JPEG, starting at quality 85, stepping down by 5 until the result is under 7MB (giving myself a 1MB buffer)</li></ul><p><strong>Then the most important line of the whole function</strong>: upload back to S3 with ContentType='image/jpeg' explicitly set.</p><p>If you skip this, S3 stores the object with Content-Type: application/octet-stream. The image works fine in a browser (it &quot;downloads&quot;), but Instagram's crawler sees a non-image MIME type and rejects it. This cost me an hour. Don't repeat my mistake.</p><p><strong>4. Post to Instagram.</strong> The Graph API requires a two-step dance:</p><ol><li>POST /{ig-user-id}/media with the image_url and caption. This creates a &quot;container&quot; and returns a creation_id.</li><li>POST /{ig-user-id}/media_publish with that creation_id.</li></ol><p>If you call step 2 too early, you get &quot;Media ID is not available&quot;. The container is created synchronously but <em>processed</em> asynchronously — Instagram fetches and validates the image in the background, and until that's done the container isn't publishable.</p><p>The fix is to poll: GET /{container_id}?fields=status_code every few seconds until status_code == &quot;FINISHED&quot;. I poll up to 15 times at 3-second intervals. In practice it's usually ready after the first or second check.</p><p><strong>5. Move the photo.</strong> S3 doesn’t have a rename operation, so “move” is actually copy + delete. Source goes from pending/xxx.jpg to posted/xxx.jpg.</p><p><strong>6. Increment </strong><strong>posted_count.</strong> A simple UpdateItem with SET posted_count = posted_count + :val.</p><h3>Step 8: Secrets in Parameter Store</h3><p>The Instagram access token and business account ID go into AWS Systems Manager Parameter Store as SecureString parameters (encrypted at rest with KMS). I grant the Lambda ssm:GetParameter permission scoped to my parameter path only.</p><p>The token I’m using is a short-lived one (~60 days). For a personal bot, refreshing it manually a few times a year is fine. For anything shared, you’d want to exchange for a long-lived token and automate the refresh.</p><h3>Step 9: The EventBridge Schedule</h3><p>A cron rule, 12:00 UTC = 21:00 JST, with the Lambda as the target. In CDK it’s three lines.</p><p>That’s the whole bot.</p><h3>Running Cost</h3><p>Rough math for 30 posts per month:</p><ul><li><strong>S3 storage</strong> — negligible (a few cents)</li><li><strong>Lambda invocations</strong> — free tier covers it</li><li><strong>DynamoDB on-demand</strong> — free tier covers it</li><li><strong>CloudFront</strong> — the first 1TB of transfer is free</li><li><strong>EventBridge</strong> — 30 invocations is a rounding error</li></ul><p>Total: <strong>under $0.10/month</strong>. Cheap enough that I don’t even think about it.</p><h3>The Traps I Hit, in Order</h3><p>Worth pulling out because if you’re building something similar, you’ll hit some subset of these:</p><ol><li><strong>Pre-signed S3 URLs don’t work with Instagram.</strong> They contain auth tokens; Instagram rejects them. Use CloudFront.</li><li><strong>CloudFront URLs downloaded as files, not images.</strong> Because S3 stored them with application/octet-stream. Set ContentType='image/jpeg' when uploading.</li><li><strong>iPhone photos are too big.</strong> 15MB+ vs. Instagram’s 8MB limit. Resize and compress in Lambda.</li><li><strong>Pillow doesn’t work out of the box.</strong> Local pip install produces binaries for the wrong platform. Build the layer in CloudShell with the right platform flags.</li><li><strong>“Media ID is not available” on publish.</strong> Instagram’s container is created synchronously but processed async. Poll for status_code == FINISHED before publishing.</li><li><strong>Wrong Instagram business account ID.</strong> The Graph API Explorer can lie about which account a token maps to. Always verify with me?fields=id,name before using an ID.</li></ol><h3><em>Note: API details reflect April 2026. The Instagram Graph API changes frequently — always cross-reference Meta’s official docs for the current behavior.</em></h3><img alt="" height="1" src="https://medium.com/_/stat?event=post.clientViewed&amp;referrerSource=full_rss&amp;postId=222c2a96299d" width="1" /><hr /><p><a href="https://blog.stackademic.com/i-built-an-aws-bot-that-auto-posts-my-poetry-to-instagram-every-day-222c2a96299d">I Built an AWS Bot That Auto-Posts My Poetry to Instagram Every Day</a> was originally published in <a href="https://blog.stackademic.com">Stackademic</a> on Medium, where people are continuing the conversation by highlighting and responding to this story.</p>
